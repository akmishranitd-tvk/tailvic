# Tailvic agent instructions

## Start here

Read `README.md` and `docs/handover.md` first. Read `docs/architecture.md` before
changing application behaviour, and `docs/operations.md` before deployment.
The repository is the source of truth; local backup folders and old chat history
are not required. Use the current files and Git history to verify dated notes.

## What is deployed

- Live site: https://tailvic.in/ (also https://www.tailvic.in/).
- Vercel workspace/project: `tailvic/tailvic-demo`.
- Production is a static HTML/CSS/JavaScript export generated by
  `scripts/export_preview.py`; the output is `public/` and is not committed.
- Flask/Jinja and seeded temporary SQLite render the export. `app.py` also
  contains a separate database-backed application, which is not deployed.
- Current browser-only customer/admin roles are not secure authentication.
  Do not put real private records behind them. Registration, OTP, saved bookings,
  payments and editing are not available in production.

## Commands

Use Python 3.11 and a project virtual environment. See README for Windows setup.

```sh
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
python scripts/export_preview.py
python -m http.server 5008 --bind 127.0.0.1 --directory public
```

Preview the generated site at http://127.0.0.1:5008/. Running `app.py` instead
starts the separate backend and does not reproduce production account/booking
behaviour. The existing suite has 25 checks as of 2026-11-20; count may evolve.

## Make changes

- Keep the selected responsive design and existing stack unless the task changes
  them. Edit templates, content or static assets, then regenerate the site.
- Do not edit `public/` as source or commit it. Do not copy an older backup over
  current repository changes.
- Keep service names, prices and business claims consistent across affected
  pages. Do not introduce competitor names, external price comparisons or a
  published-reference table into Tailvic service/pricing content.
- The owner requested no visible demo banners or displayed login credentials.
  Keep technical limitations explicit in developer documentation and keep
  unavailable actions disabled or routed to the existing contact page.
- Use `specs/change-template.md` for substantial behaviour changes. Describe
  acceptance criteria and unresolved decisions before implementing them.
  Small copy/layout fixes do not need a separate spec.
- Add meaningful checks when behaviour changes; use the existing suite and
  visual inspection for copy/layout changes. Update relevant docs in the same
  commit when behaviour, deployment or operational assumptions change.

## Commit, deploy and verify

- Fetch before starting shared work. Preserve teammates' changes and use your
  actual Git identity. Do not force-push shared history.
- When the request includes deployment, commit the reviewed changes and push
  to `main` if repository policy permits. This triggers production deployment;
  no separate manual Vercel deploy is normally needed. If using a feature branch,
  merge it into `main` through the team's normal process to publish.
- For changes without deployment authorization, use a feature branch. Existing
  pull-request CI runs checks but does not publish a preview or production.
- Watch the GitHub Actions run for the pushed commit until completion. A push
  alone is not proof of deployment. Fix failures and verify the rerun.
- Verify the changed page at https://tailvic.in/ after success, including desktop
  and mobile when layout changes. Check the actual requested behaviour; HTTP 200
  alone is insufficient. Capture screenshots when browser tools are available.
- Report commit, pipeline result, live URL and any unverified limitations. If
  browser access is unavailable, state which HTTP/content checks were used.

## Credentials and scope

Use the existing GitHub Actions deployment secrets; do not ask for tokens in
chat or commit credentials, `.env`, `.vercel/`, databases or session keys.
Do not replace the existing Vercel project, change DNS, broaden token access or
add a second deployment trigger for routine site edits. See operations for
credential rotation and recovery. Real authentication/persistence requires an
explicit architecture change and acceptance criteria.
